Offline machine-learning workflow for the Embedded Programming PBL smart-irrigation prototype
(Arduino Uno + capacitive soil sensor + DHT11 + relay + 12 V pump).

It takes **soil moisture, temperature and humidity** and produces a **`WATER` / `NO_WATER`**
decision. Everything (data collection, training, evaluation, export, inference) works with no
internet and no cloud service.

## Hardware and pins

| Item | Default pin (change in the sketch and confirm on your wiring) |
|---|---|
| DHT11 DATA | D4 (`DHT_PIN`) |
| Soil sensor AOUT | A0 (`SOIL_PIN`) |
| Relay IN | D7 (`RELAY_PIN`), polarity `RELAY_ACTIVE_LOW` (true = ON when IN is LOW) |

Also: Power Supply Board V2.2, 12 V 2 A adapter, 12 V mini pump.

### Electrical architecture (pump safety)

```
Arduino digital output (D7)
        ↓
Relay input (IN)
        ↓
Relay COM / NO contacts
        ↓
12 V pump supply
        ↓
Pump
```

The model only decides; the Arduino only drives the relay's IN pin; the relay switches the pump.
**Never connect the pump to an Arduino pin.** Keep relay GND common with Arduino GND. Check whether
your relay board is active-LOW or active-HIGH before connecting the pump.

Note on the ADC: an Uno has a **10-bit ADC, so `soil_raw` is 0-1023**. The cleaner drops rows outside
that range (e.g. a value like 1150 cannot come from an Uno).

## Real workflow

### 1. Calibrate the soil sensor (the team must do this)

`soil_raw` alone is not meaningful, and the direction (higher = drier or wetter) must come from
measurement, not assumption. With `sensor_logger.ino` running:

1. Sensor in **air / bone-dry soil**: note the raw value → `soil_raw_dry`.
2. Sensor in **saturated soil or water up to the marked line**: note the raw value → `soil_raw_wet`.
3. Choose `moisture_threshold_pct`: the calibrated moisture below which *your team* decides this plant
   needs water (used by the baseline and, optionally, by the labeling rule).
4. Write all three into `config/settings.json`. They ship as `null` on purpose; nothing in the code invents them.

Moisture is computed as `(soil_raw_dry - soil_raw) / (soil_raw_dry - soil_raw_wet) × 100`, clipped to
0-100 %, so a sensor whose raw value rises with wetness also works (just put the larger value in `soil_raw_wet`).

### 2. Collect data

Flash `firmware/arduino/sensor_logger/sensor_logger.ino` (needs Adafruit *DHT sensor library*; the
relay is held OFF; you water by hand). Then:

```bash
python -m src.data_collection --list-ports
python -m src.data_collection --port COM3 --plant-id plant_1 --condition dry --session-id dry_01
```

Options: `--baud` (default 9600, must match the sketch), `--label WATER|NO_WATER` (label for the whole
session), `--max-samples`, `--duration`, `--out`, `--echo`. Ctrl+C stops cleanly; every row is flushed
as it arrives. Lines like `Soil raw: 812`, `Temperature: 29.4 C`, `Humidity: 61.0 %` are parsed
(case, `=` vs `:`, `Temp`/`Hum` and missing units are tolerated); malformed lines and DHT failures are
counted and skipped.

**Dataset format** (`data/raw/*.csv`): `timestamp, soil_raw, temperature_c, humidity_pct, plant_id,
soil_condition, irrigation_label, session_id, label_source`. The first seven are the brief's columns;
`session_id` (used to keep correlated readings together in the split) and `label_source`
(`manual` / `threshold_rule`) are added.

#### Collection methodology

Use **one session per run** with its own `--session-id`, record the same pot/soil/sensor position each
time, and keep the sensor placement fixed. Aim for many sessions (≥ 5 at the very least; more is better),
not just many rows: readings taken a minute apart in the same run are nearly duplicates.

| Condition | How | What to record |
|---|---|---|
| **Dry** | Let the soil reach a clearly dry state (the state you would water in) and log for a while | `--condition dry` |
| **Moderately moist** | After a *measured, controlled* amount of water, log as the soil settles | `--condition moist` |
| **Wet / freshly watered** | Log right after watering and keep logging as it dries | `--condition wet` |

Vary ambient conditions (morning/afternoon, sun/shade, indoor/outdoor) across sessions, otherwise
temperature and humidity carry no information. Note that a capacitive sensor takes time to respond to
new water, so the "soil is fine" state appears minutes after watering.

#### Labeling procedure

Labels must come from a **rule the team decides and writes down**, never from the model. Options:

- **Manual / independent judgement** (preferred): the team decides per session or per period whether the
  plant needed water (finger test, plant condition, weighing the pot, ...), and passes `--label` or edits
  `irrigation_label`. `label_source` = `manual`.
- **Threshold rule** to fill blanks: `python -m src.labeling data/raw/session.csv` labels empty rows
  `WATER` if calibrated moisture `< moisture_threshold_pct`, else `NO_WATER` (`label_source` = `threshold_rule`).

> **Important:** if every label comes from the threshold rule, the threshold baseline is correct *by
> construction* and no ML model can beat it. Training prints a warning in that case. ML only has something
> to learn if the labels contain information the threshold does not, e.g. the team's judgement that hot, dry
> air means "water sooner".

### 3. Train

```bash
python -m src.train
```

- Cleans data (missing/non-numeric values, impossible values, duplicates, unlabeled rows; counts per reason are reported and stored).
- **Split (leakage-aware):** whole sessions go to train or test (`group`) when there are ≥ 5 sessions,
  otherwise a chronological split (`time`). A plain random row split is available but not the default
  (`config/settings.json` → `split.strategy`) because it inflates scores on correlated readings.
  Training and test size and class distribution are printed and saved.
- **Cross-validation** on the training set only (grouped by session when ≥ 3 sessions). With a small
  dataset the run prints warnings that metrics are unstable; the warnings are never hidden.
- Candidates (small, interpretable, seeded with `random_seed`): learned soil-only threshold,
  Logistic Regression, small Decision Tree (depth 3), small Random Forest (10 trees, depth 3).
- **Model selection rule (fixed in advance):** highest mean CV F2 (recall on `WATER` weighted higher than
  precision), ties within 0.01 go to the most Arduino-friendly model. The test set is not used to choose.
- Saves the models and `metadata.json` (feature order, calibration, seed, split sessions, CV results,
  data-file hashes, library versions) in `models/`.

### 4. Evaluate

```bash
python -m src.evaluate
```

Scores every candidate **and the threshold baseline** on the held-out test set and writes
`reports/model_report.md` + `reports/figures/`: accuracy, precision, recall, F1, confusion matrices, and
the comparison table with embedded suitability. It states plainly whether ML beats the baseline; if it does
not, the report says so.

**Why false negatives matter:** with `WATER` as the positive class, a false negative means the plant
needed water and the model said `NO_WATER`; the plant dries out. A false positive wastes some water.
For a plant that can be stressed by drought, FNs usually cost more than FPs, so recall on `WATER` (and F2)
is reported and used for selection rather than accuracy alone.

### 5. Predict on the PC

```bash
python -m src.predict --soil 800 --temperature 29 --humidity 60     # soil = RAW sensor value
```

Prints the model decision and the baseline decision.

### 6. Export to Arduino

```bash
python -m src.export_embedded                       # selected model -> firmware/arduino/ml_controller/model.h
python -m src.export_embedded --model decision_tree
```

Generates `model.h`: the calibration constants, `soilRawToMoisturePct()`, and `needsWater()` as readable
nested `if` statements with a comment naming the feature at each split (decision tree), or three
multiply-adds (logistic regression, scaler folded in). Also writes `models/embedded_model.md`, a plain-language
description of the logic. Thresholds come from the trained model; none are hard-coded. Random Forest is not
exported (too many nodes to audit comfortably on an Uno; documented as such).

**Consistency check (automatic):** the exporter compiles `model.h` with g++ and compares its output with
the Python model on every stored train/test row, thousands of random inputs, inputs sitting exactly on and
next to each tree threshold, and every one of the 1024 possible ADC values. If a single decision differs, the
header is **not** written. Thresholds are emitted as the largest `float32` ≤ the trained threshold so the
32-bit AVR `float` compares identically to scikit-learn.

### 7. Run the controller on the Arduino

`firmware/arduino/ml_controller/ml_controller.ino`: reads the soil sensor (same 10-sample average as the
logger), DHT11, applies the training-time calibration, runs `needsWater()`, drives the relay, runs the pump
for `PUMP_RUN_MS`, waits `SOAK_TIME_MS`, and prints every input and the decision to Serial.

Beyond the brief it adds fail-safes: the relay is set OFF before the pin becomes an output, a failed DHT
read means no watering, and `MAX_WATERINGS_PER_DAY` caps watering regardless of the model. Pump time, soak
time and the cap are `#define`s, **set by the team; the defaults are placeholders, not tuned values**.

Verification status: both sketches pass a syntax check against stub Arduino headers, and the exported `model.h`
is compile-tested and compared against Python. **The sketches have not been compiled with the real Arduino
toolchain or run on hardware.**

## Machine-learning concepts (short version)

- **Why ML at all?** A fixed threshold looks at soil moisture only. The same reading may call for watering
  sooner when the air is hot and dry than when it is cool and humid. A small model can learn such a
  combination from data, *if* the data show it. If they do not, the threshold is just as good, and the
  project should say so.
- **Inputs:** calibrated soil moisture (or raw), temperature, humidity. Timestamp, plant ID, session and the
  text condition are **not** features.
- **Target:** `WATER` / `NO_WATER`; a classification that maps directly onto the relay.
- **Data:** real readings from the prototype, labeled by the team's documented rule.
- **Preprocessing:** cleaning, missing-value removal, calibration to moisture %, fixed feature order; scaling
  only for logistic regression (folded into the exported weights).
- **Training:** each model picks parameters that best match the labels on the training rows: a tree learns
  "if moisture ≤ x then ..." splits; logistic regression learns a weighted sum. Small models are used on
  purpose so they can be read, checked, and fit on an Uno.
- **Evaluation:** compare against the baseline on data the model never saw, using precision, recall, F1,
  the confusion matrix, and especially false negatives.
- **Deployment / offline:** the small tree becomes plain C `if` statements compiled into the sketch. Inference
  is a few comparisons on the Arduino itself. No network, cloud, or PC is needed at run time; the PC is only
  used to train.

## Limitations

- No real data yet; nothing here is evidence about the real plant until it is collected.
- One sensor, one soil, one plant: a model does not transfer to other soils/sensors without recalibration and new data.
- Correlated readings mean the effective sample size is nearer the number of sessions than the number of rows.
- Capacitive sensors drift and respond slowly; DHT11 is coarse (±2 °C, ±5 % RH).
- The binary decision has no notion of *how much* water is needed; pump duration is a fixed team setting.
- Firmware not verified on hardware.
